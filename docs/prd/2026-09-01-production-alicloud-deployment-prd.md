# 阶段 1：生产配置与同源 API 改造 PRD

文档日期：2026-09-01
文档状态：已确认（2026-09-01）
对应路线图：阶段 1「生产配置与同源 API」

## 1. 背景与问题

当前系统可以在本地开发环境运行，但尚不具备安全、稳定地部署到阿里云测试环境的基础：

1. 前端运行时代码在多个位置写死 `http://localhost:8080/api`。部署后，学生浏览器中的 `localhost` 会指向学生自己的电脑，无法访问服务器。
2. Django 当前使用固定 `SECRET_KEY`、`DEBUG=True`、`ALLOWED_HOSTS=['*']` 和全开放 CORS，不符合生产环境安全要求。
3. 开发、自动化测试和生产环境没有清晰的配置边界，容易把开发设置带入生产环境。
4. 系统没有可供部署平台使用的存活/就绪检查，也缺少适合生产排障的日志配置。
5. 生产错误不应向学生或教师暴露调试堆栈、密钥、请求正文等敏感信息。

本阶段只建立后续数据库迁移和云端部署所需的配置基础，不在本阶段购买或配置阿里云资源。

## 2. 目标

1. 前端所有业务请求统一通过一个 API 配置入口，默认使用同源 `/api`。
2. 本地开发时由 Vite 将 `/api` 代理到本地 Django，保持现有开发体验。
3. Django 的敏感项和环境相关项通过环境变量配置，并明确开发、测试、生产三类运行边界。
4. 生产模式默认采用安全配置：`DEBUG=False`、无固定密钥、无通配主机、无全开放 CORS。
5. 提供存活检查、数据库就绪检查和可用于云端收集的控制台日志。
6. 通过自动化测试、Django 部署检查、前端构建和手工联调验证本阶段改造。

## 3. 非目标

以下内容不在阶段 1 实施，继续按总路线图推进：

- 不接入 MySQL 或 RDS，不迁移当前 SQLite 数据。
- 不修改学生密码存储、Token 生命周期或业务权限模型。
- 不修复小测可信度问题。
- 不拆分或隔离学生代码 Runner。
- 不引入 Docker、Gunicorn、Nginx、HTTPS 或阿里云资源。
- 不全面改造既有业务错误响应格式；仅保证生产环境不泄露调试信息，并为新增健康检查定义稳定响应。
- 不解决阶段 9 中已有的全量测试、Lint 或构建停滞问题；若这些问题阻碍阶段 1 验证，则记录基线并对阶段 1 相关范围进行独立验证。

## 4. 用户故事

### 4.1 学生

- 作为学生，我通过网站域名访问课程时，页面能够自动访问同一域名下的后端，不需要知道服务器端口。
- 作为学生，当服务暂时不可用时，我看到可理解的失败提示，而不是 Django 调试页面或内部堆栈。

### 4.2 教师

- 作为教师，我在登录和管理页面中的所有请求使用统一的 API 地址，部署后不需要逐页修改代码。
- 作为教师，我在本地开发环境仍可按现有方式启动前后端并完成联调。

### 4.3 运维人员

- 作为运维人员，我可以仅通过环境变量切换开发、测试和生产配置。
- 作为运维人员，我可以通过健康检查区分“Web 进程存活”和“数据库可用”。
- 作为运维人员，我可以从标准输出日志中看到时间、级别、模块和错误信息，但日志不记录密码、Token、Cookie 或完整请求正文。
- 作为运维人员，如果生产密钥或允许访问的域名没有正确配置，应用应拒绝以不安全配置启动。

## 5. 功能需求

### 5.1 前端统一 API 地址

1. 建立唯一的前端 API 基础地址配置入口。
2. 默认 API 基础地址为同源 `/api`。
3. 允许通过 `VITE_API_BASE_URL` 在特殊环境覆盖基础地址；变量为空或未设置时仍使用 `/api`。
4. 清除业务运行时代码中写死的 `http://localhost:8080/api`，包括学生 API、聊天 API、教师登录和教师管理页面。
5. 统一处理基础地址与路径之间的斜杠，避免产生 `//` 或漏掉 `/`。
6. 本地 Vite 开发服务器将 `/api` 代理到 `http://127.0.0.1:8080`；浏览器侧仍只请求 `/api`。
7. API 客户端保留现有鉴权和业务行为，不在本阶段改变接口契约。

### 5.2 Django 环境配置

1. 使用明确的运行环境标识区分 `development`、`test`、`production`，默认值为 `development`。
2. 以下配置支持环境变量：
   - `DJANGO_SECRET_KEY`
   - `DJANGO_DEBUG`
   - `DJANGO_ALLOWED_HOSTS`
   - `DJANGO_CORS_ALLOWED_ORIGINS`
   - `DJANGO_CSRF_TRUSTED_ORIGINS`
   - 日志级别
3. 逗号分隔的列表配置应去除空白和空值；布尔值只接受清晰、可预测的合法写法。
4. 开发环境允许使用便于本机调试的默认值，但不得把这些默认值作为生产设置。
5. 测试环境保持测试数据库隔离和稳定的自动化测试行为。
6. 生产环境必须满足：
   - `DEBUG=False`；
   - `DJANGO_SECRET_KEY` 必须显式设置，且不能等于仓库中的开发默认值；
   - `ALLOWED_HOSTS` 必须显式设置且不能包含 `*`；
   - 默认不启用跨域；同源部署不依赖 CORS；
   - 若确需跨域，只允许显式列出的 HTTPS 来源；
   - CSRF 信任来源只能来自显式列表；
   - 关键配置缺失或明显不安全时，应用启动失败并给出不含密钥值的说明。
7. 提供不包含真实凭据的环境变量示例文件，并确保真实环境文件不被 Git 提交。

### 5.3 健康检查

1. 增加 `GET /api/health/live/`：只判断 Django 进程能否处理请求，不访问数据库。
2. 增加 `GET /api/health/ready/`：执行轻量数据库连通性检查。
3. 存活时返回 HTTP 200 和稳定 JSON：`{"status":"ok"}`。
4. 就绪时返回 HTTP 200；数据库不可用时返回 HTTP 503，响应不得包含数据库地址、账号、SQL 或异常堆栈。
5. 两个端点均无需登录，不读取或修改业务数据。

### 5.4 日志与生产错误

1. 日志输出到标准输出，至少包含时间、日志级别、logger 名称和消息，便于后续由阿里云或容器平台收集。
2. 日志级别可通过环境变量调整，生产默认 `INFO`。
3. 未处理异常记录在服务端日志中；生产响应不暴露调试堆栈或本地路径。
4. 默认不记录密码、Token、Cookie、Authorization 请求头、AI 密钥或完整请求正文。
5. 健康检查正常请求不产生高噪声日志；就绪检查失败应有可定位但不泄密的错误日志。

## 6. UI / UX 要求

- 不新增页面，不改变现有导航和视觉设计。
- 登录、题库、聊天、教师管理等现有功能的操作流程保持不变。
- 前端网络错误继续使用现有页面的提示机制；本阶段只统一底层请求地址，不进行全站提示样式重构。
- 健康检查只服务部署和运维，不在学生或教师界面展示。

## 7. 资源与约束

- 当前开发环境为 macOS，本阶段不依赖购买云服务器或 RDS。
- 当前后端仍使用 SQLite；数据库就绪检查必须同时兼容 SQLite，并为阶段 2 接入 MySQL 保留通用实现。
- 不提交任何真实生产域名、密钥、数据库密码或第三方 AI 凭据。
- 尽量少引入新依赖；环境变量解析优先使用标准库和 Django 现有能力。
- 保持现有 API 路径和响应结构兼容，避免给后续业务阶段制造无关回归。

## 8. 非功能要求

### 8.1 安全性

- 生产环境必须安全失败，不能在缺少关键配置时自动退回开发默认值。
- 生产环境不允许 `DEBUG=True`、固定开发密钥、`ALLOWED_HOSTS=['*']` 或全开放 CORS。
- 示例配置和日志中不得出现真实凭据。

### 8.2 可维护性

- API 地址和 Django 环境配置均只有一个权威入口。
- 新增配置项必须在示例环境文件和开发文档中说明用途、格式和示例。
- 配置解析、生产安全校验和健康检查应有自动化测试。

### 8.3 可观察性

- 健康端点响应稳定，可直接用于后续负载均衡或容器健康检查。
- 关键启动错误和运行异常可在标准输出日志中定位。

### 8.4 兼容性

- 本地开发无需把后端开放为跨域服务即可完成前后端联调。
- 现有后端路由和业务接口保持不变。

## 9. 验收标准与验证方法

### 9.1 静态检查

- 在 `frontend/src` 运行搜索后，业务运行时代码中不存在 `http://localhost:8080/api` 或等价写死地址。
- 仓库中不存在真实生产密钥或凭据。
- 环境变量示例覆盖阶段 1 的全部配置项。

### 9.2 后端自动化验证

- 配置解析测试覆盖开发、测试、生产模式。
- 测试证明生产环境缺少密钥、使用通配主机或启用调试时会拒绝启动。
- 健康检查测试覆盖：存活 200、数据库就绪 200、数据库异常 503、响应不泄露异常详情。
- 阶段 1 新增/修改的后端测试全部通过。
- 使用一组安全的临时生产环境变量运行 `python manage.py check --deploy`，不出现由阶段 1 配置导致的高风险警告。

### 9.3 前端自动化验证

- API 基础地址测试覆盖默认 `/api`、环境变量覆盖和斜杠处理。
- 受影响页面或 API 模块测试证明请求使用统一入口。
- 阶段 1 新增/修改的前端测试全部通过。
- 前端生产构建能够完成；若确认是既有阶段 9 基线问题导致失败，必须提供可复现命令、错误证据和阶段 1 范围的替代验证，不得把失败描述为通过。

### 9.4 手工联调验证

1. 启动本地 Django `127.0.0.1:8080`。
2. 启动 Vite 开发服务器，不设置 `VITE_API_BASE_URL`。
3. 浏览器 Network 面板确认页面请求为当前前端域名下的 `/api/...`，而非 `localhost:8080`。
4. 验证学生登录、教师登录，并各抽查一个学生接口和教师管理接口。
5. 访问 `/api/health/live/` 与 `/api/health/ready/`，确认均返回 200 和约定 JSON。
6. 使用生产模式的安全临时变量启动配置检查，确认 `DEBUG=False`、主机白名单和同源策略生效。
7. 分别移除生产密钥、设置通配主机，确认应用明确拒绝不安全启动。

## 10. 成功指标

- 前端运行时代码硬编码 API 地址数量：从 8 处降为 0 处。
- 生产模式中的固定密钥、开放 CORS、通配主机和 `DEBUG=True`：均为 0。
- 两个健康检查端点按约定返回状态码，相关测试通过率 100%。
- 阶段 1 新增及受影响测试通过率 100%。
- 本地同源代理联调覆盖学生端和教师端各至少 1 条完整请求链路。

## 11. 风险与回滚

- 风险：统一 API 地址时遗漏教师页面的独立请求。对策：静态搜索与页面测试双重检查。
- 风险：生产校验过严导致本地测试无法启动。对策：显式区分环境，并为配置分支编写测试。
- 风险：代理配置掩盖路径拼接问题。对策：对基础地址规范化单独测试，并在浏览器 Network 面板复核。
- 风险：日志误记录敏感信息。对策：不启用请求正文日志，测试错误响应不含异常详情。
- 回滚方式：本阶段改动均为代码和配置文件，可按提交回退；不涉及数据库结构和数据迁移。
