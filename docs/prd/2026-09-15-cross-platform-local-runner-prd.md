# 跨平台本机 Runner 过渡方案 PRD

日期：2026-09-15
状态：用户已确认（2026-09-15）

## 1. 背景与问题

AI 课学生端当前已经切换到异步执行架构：Django 只创建 `ExecutionTask`，前端轮询任务状态，独立 Runner 负责领取、执行并回写结果。Web 侧队列、HMAC 私有协议、租约、结果校验、成绩落库和前端状态展示已经完成，但 Docker Runner 尚未实施，因此代码任务会停留在 `queued`。

近期目标是在暂不接入 Docker 的前提下恢复学生代码运行与自动评测，同时保留当前异步架构，为以后切换 Docker 沙箱保留稳定边界。开发首先在 `MacBook` 分支和当前 macOS 电脑验证，随后迁移到 Windows 机房电脑对应的 `jifang3` 分支。

本方案是校内受控环境的过渡能力，不等同于 Docker 或虚拟机级别的安全隔离。

## 2. 目标

1. 学生可以在 AI 课普通练习和 AI 混合小测中运行 Python 代码。
2. 学生点击“保存并提交”后，代码、提交记录、评测结果和成绩能够正确持久化。
3. 保留现有 `queued -> running -> final` 异步状态和页面刷新恢复能力。
4. Runner 与 Django 分进程运行，学生代码不在 Django 请求进程内执行。
5. 使用固定执行槽控制全局并发，支持约 40 名学生在课堂集中操作。
6. 同一套 Runner 核心代码兼容 macOS 和 Windows，不要求 Docker、WSL 或 Unix 专属命令。
7. 当前 MacBook 验证通过后，可以低冲突迁移到 `jifang3` 分支，并由 Windows 启停脚本管理。
8. 将来接入 Docker 时，仅替换执行后端，不改变公共 API、任务模型和前端交互。

## 3. 非目标

1. 本阶段不提供强沙箱、内核隔离、文件系统隔离或可靠的断网能力。
2. 本阶段不允许把服务直接暴露到公网供不受信任用户执行任意代码。
3. 本阶段不安装或配置 Docker。
4. 本阶段不重写现有题库、评分规则、AI 混合小测结算逻辑或前端编辑器。
5. 本阶段不把 Django、前端或数据库容器化。
6. 本阶段不承诺在当前 8GB MacBook Air 上同时运行 40 个 Python 子进程；40 人请求通过有限执行槽排队消化。

## 4. 用户故事

### 4.1 学生运行代码

作为学生，我点击“运行”后能看到排队和运行状态，并在有限时间内得到标准输出、标准错误、超时或资源错误提示。

### 4.2 学生保存并提交

作为学生，我点击“保存并提交”后，本次代码快照立即保存；Runner 根据服务端测试快照评测，最终成绩和逐测试点结果可查询，重复点击或网络重试不会重复计分。

### 4.3 混合小测

作为参加 AI 混合小测的学生，我提交编程题后，评测结果可以触发现有小测结算，不因使用本机 Runner 改变截止时间、快照或计分规则。

### 4.4 教师课堂使用

作为教师，我可以让约 40 名学生集中运行或提交；系统通过固定并发和公平队列保持 Web 页面可用，不因某个学生死循环而永久占用执行槽。

### 4.5 机房维护

作为机房维护者，我可以在 Windows 上通过批处理脚本同时启动和停止 Django、Vite 与 Runner，并从日志判断 Runner 是否在线。

## 5. 功能范围

### 5.1 Runner Controller

- 使用现有 HMAC 协议上报节点心跳、领取任务、续租和回写结果。
- 支持可配置的固定并发槽。
- 空队列时退避轮询，避免持续占用 Django 和数据库。
- Web 或网络短暂异常时有限重试，不重复领取或重复完成任务。
- 收到终止信号时停止领取新任务，等待或终止活动任务后退出。
- 启动时校验关键配置，不在日志中输出服务密钥、学生完整代码或隐藏测试答案。

### 5.2 本机执行后端

- 每次任务使用独立临时目录和独立 Python 子进程。
- 子进程使用与 Runner 明确配置的 Python 解释器，不依赖命令名碰巧解析成功。
- 普通运行支持 `stdin`、`stdout` 和 `stderr`。
- 自动评测按服务端冻结测试快照逐测试点运行并计算结构化结果。
- 强制限制单次和整任务墙钟时间。
- 输出按字节上限截断；超限、超时或停止时终止整个子进程树。
- 执行结束后删除临时目录，不保留学生代码文件。
- macOS 与 Windows 分别使用平台适配的进程树终止逻辑。

### 5.3 状态与故障恢复

- 沿用现有任务租约和最多重试次数。
- Runner 存活时持续触发过期任务恢复，不能让过期任务永久保持 `queued`。
- Runner 未在线时，启动脚本和日志必须给出明确提示。
- 前端继续使用现有有限轮询和活动任务恢复逻辑。
- 系统错误保持 `score = NULL`，不得伪造成学生得 0 分。

### 5.4 跨平台启停

- macOS/Linux：更新 `start_all.sh`、`stop_all.sh`，纳入 Runner 进程和日志。
- Windows：更新 `start_all.bat`、`stop_all.bat`，纳入 Runner 进程及其子进程树。
- Python 路径选择遵循各平台现有项目虚拟环境规则。
- 配置通过示例环境文件说明；真实密钥不进入 Git。

## 6. 并发与资源约束

### 6.1 默认配置

| 环境 | 默认执行槽 | 建议用途 |
| --- | ---: | --- |
| 当前 M1 / 8GB MacBook | 2 | 开发、功能验证和小规模联调 |
| Windows 机房主机 | 由硬件验收确定，初始 4 | 课堂试运行 |
| 8 核 / 16GB 专用主机 | 6–8 | 约 40 人集中操作 |

### 6.2 单任务限制

- 普通运行：最长 10 秒。
- 自动评测：单测试点最长 5 秒，整任务最长 30 秒。
- 输出总量：最多 128 KiB。
- 单学生：最多 1 个运行中任务和 2 个排队任务，沿用现有 Web 约束。
- 队列 TTL：从当前 120 秒调整为适合课堂峰值的 300 秒，并通过压测复核。

### 6.3 40 人含义

“支持 40 人同时使用”指 40 个已登录学生可以在短时间窗口集中创建任务，Web 保持响应，任务不丢失、不重复并最终进入明确终态；不表示同时启动 40 个执行子进程，也不保证所有恶意超时任务在数秒内结束。

## 7. 安全边界

本机 Runner 只能降低可用性风险，不能视作不受信任代码的安全沙箱：

- 学生代码原则上可能读取运行账号可读文件、访问本机网络或调用系统能力。
- Runner 必须使用专门的低权限系统账号运行，不得使用管理员账号。
- Runner 环境不得包含生产数据库密码、第三方 AI 密钥或教师管理凭据。
- 机房阶段仅允许受控校园网和已认证学生使用。
- 页面、README 和部署文档须标注“本机 Runner 过渡模式”。
- 公网或更高安全等级使用前必须切换 Docker/虚拟机沙箱并完成恶意代码验收。

## 8. UI/UX 规格

- 保持现有“排队中、运行中/评测中、成功、答案错误、运行错误、超时、资源超限、系统错误”状态展示。
- 不恢复同步长请求，不移除现有页面刷新恢复能力。
- Runner 不可用或轮询超时时使用明确中文提示，不无限显示“排队中”。
- 结果必须对应提交时的代码快照，而不是编辑器当前内容。

## 9. Windows 迁移要求

1. Runner 核心模块不得依赖 `fork`、`resource`、Unix signal 语义、`bash` 或 `/tmp`。
2. 临时目录使用 Python 标准库跨平台接口。
3. Windows 终止任务必须终止完整进程树，不能只杀父 Python 进程。
4. 文件编码统一 UTF-8，批处理脚本输出必须可读，不延续当前乱码问题。
5. `MacBook` 与 `origin/jifang3` 当前以 `12bb081` 为共同基线；`jifang3` 只有少量跨平台与排序增量。实施应形成独立、可挑选或合并的提交，避免覆盖机房分支改动。
6. 迁移后必须在真实 Windows 机房电脑执行专项验收，macOS 测试不能代替 Windows 进程树和路径验证。

## 10. 非功能需求

- 正确性：同一幂等键只产生一个任务；每个任务最多应用一次最终结果。
- 可恢复性：浏览器刷新、Runner 重启和 Django 短暂重启后，任务进入成功、失败、重试或取消之一，不永久悬挂。
- 可观测性：日志包含 Runner ID、任务 ID、状态和耗时，不包含代码、密钥和隐藏答案。
- 可维护性：协议客户端、任务调度、执行后端和评测逻辑分层；以后新增 Docker executor 不改 Controller 主流程。
- 兼容性：支持项目当前 Python 版本范围和 macOS/Windows 主流环境。

## 11. 成功指标与验收标准

### 11.1 自动验证

- Runner HMAC、重试、防重放、心跳、领取、续租和完成测试通过。
- 普通运行覆盖正常输出、标准输入、语法错误、运行错误、超时和超大输出。
- 自动评测覆盖全对、部分错误、全部错误、运行错误、超时和多测试点。
- AI 普通练习与混合小测现有测试全部通过。
- macOS 与 Windows 平台适配逻辑均有自动测试。

### 11.2 本机端到端

- 当前 MacBook 上从学生页面完成至少一次运行和一次正式提交。
- 数据库状态实际经历 `queued -> running -> final`。
- Runner 停止后不产生永久排队；重启后恢复策略符合任务租约。
- 关闭页面再进入可以恢复活动任务或看到最终成绩。

### 11.3 并发验收

- 使用至少 40 个模拟学生并发创建运行或评测任务。
- Web 创建任务无数据损坏和重复成绩。
- 实际运行子进程数不超过配置的执行槽。
- 全部任务最终进入明确终态，记录 P50/P95 排队时间和总完成时间。
- SQLite 只做本机功能验证；40 人正式验收使用 MySQL。

### 11.4 Windows 验收

- `jifang3` 分支在机房电脑完成安装、迁移、启动和停止。
- 中文日志与启动脚本可读。
- 正常、错误、死循环和子进程用例均能结束且无残留执行进程。
- 40 人规模验收结果达到课堂可接受范围后再开放使用。

## 12. 发布与回退

- `CODE_EXECUTION_ENABLED` 继续作为总开关。
- 本机 Runner 异常时可停止 Runner 并关闭开关，不影响登录、课程、选择题和历史成绩。
- 不恢复 Django Web 进程直接执行学生代码的旧路径。
- MacBook 验证完成后再迁移 `jifang3`，不直接在两个分支并行开发同一功能。
