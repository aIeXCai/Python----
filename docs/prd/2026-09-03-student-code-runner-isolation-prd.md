# 阶段 5：学生代码 Runner 隔离 PRD

文档日期：2026-09-03

对应路线图：阶段 5「学生代码 Runner 隔离」

## 1. 背景与问题

平台目前有两条学生代码执行链路：

1. “运行代码”接口将代码写入系统临时文件，然后由 Django Web 进程直接调用当前 Python 解释器执行，单次超时 10 秒。
2. “提交评测”先把代码写入后端 `submissions/` 目录，再由 Django Web 进程针对每个测试点直接启动 Python 子进程，单测试点超时 5 秒。

现有实现虽然具备登录校验、简单频率限制和执行超时，但不能作为互联网环境中的安全边界：

- 学生代码与 Django 共享主机、用户权限、网络、环境变量和文件系统视野。
- 学生代码可能访问生产数据库、第三方服务、公网、后端源码或其他学生文件。
- 无限循环有超时，但内存耗尽、进程炸弹、后台子进程和超大输出没有可靠限制。
- 代码执行同步占用 Web 请求和 Gunicorn worker；课堂集中运行时可能拖垮登录、小测和教师后台。
- 自动评测按测试点逐次启动进程，缺少整次任务总时限、全局队列、公平调度和容量保护。
- 临时文件和永久 `submissions/` 文件的边界不清晰，无法证明任务结束后执行环境已彻底清理。
- Web 端直接返回底层执行错误，存在泄露本地路径、运行环境或内部异常的风险。

因此，正式部署前必须把所有不可信学生代码从 Django Web 进程和生产数据平面中拆出，由独立 Runner 在一次性沙箱内执行。

## 2. 产品目标

1. Django Web 进程不再直接启动或执行任何学生代码。
2. “运行代码”和“提交评测”统一进入受控任务队列，并由独立 Runner 服务处理。
3. 每次任务使用独立、非 root、无网络、只读根文件系统的一次性沙箱。
4. 对执行时间、CPU、内存、进程数、输入、输出和临时空间设置服务端硬限制。
5. 恶意或失控代码只能导致自己的任务失败，不能影响 Web、数据库、其他学生任务或 Runner 控制面。
6. 课堂高峰时提供有界队列、公平调度、状态反馈和过载保护，不让代码执行压垮基础教学功能。
7. 保持现有 Python 运行、标准输入、自动评测、成绩和提交历史的主要使用体验。
8. Runner 不可用时，登录、课程浏览、信息课小测、成绩查看和教师管理仍可正常使用。

## 3. 非目标

本阶段不包含：

- 不正式购买或部署阿里云 ECS、RDS、负载均衡和域名；云端部署属于阶段 10。
- 不完成 Nginx、Gunicorn 和完整生产编排；部署文件整合属于阶段 8。
- 不支持 Java、C/C++、JavaScript 等多语言运行环境。
- 不提供交互式终端、持续输入、调试器、图形界面、GPU 或长期运行任务。
- 不允许学生安装第三方包，也不为单题提供自定义系统依赖。
- 不改变现有题目评分规则、最高分统计和教师成绩查看逻辑。
- 不新增抄袭检测、代码相似度分析或 AI 自动点评。
- 不在本阶段确定学生代码和提交记录的长期保留期限；数据治理统一在阶段 7 明确。
- 不把容器本身视为唯一安全措施；Runner 主机与 Web/RDS 的网络隔离仍是上线门槛。

## 4. 用户角色

### 4.1 学生

- 登录后可运行当前代码并提供标准输入。
- 可提交代码进行自动评测。
- 可看到排队、运行、成功、运行错误、超时、资源超限和系统繁忙等状态。
- 只能查询自己的执行任务和提交结果。

### 4.2 教师

- 继续查看学生提交、得分、状态和错误摘要。
- Runner 故障时能区分“学生代码错误”和“系统执行服务异常”。
- 不需要接触 Runner 管理接口或手工清理执行文件。

### 4.3 Web 服务

- 完成身份校验、参数校验、题目权限校验、任务创建和结果持久化。
- 不解释、不导入、不执行学生代码。
- 只通过私有、鉴权的 Runner 通道投递任务和接收结果。

### 4.4 Runner 服务

- 只接受 Web 服务创建的合法任务。
- 在受限沙箱中执行代码，采集有限输出并返回结构化结果。
- 不持有生产数据库账号、Django 密钥、AI 密钥或用户 Token。
- 任务结束后销毁沙箱和临时文件。

## 5. 核心产品决策

1. **两类任务统一隔离**：自由运行与正式提交都必须经过 Runner，不能只隔离其中一条链路。
2. **一次执行一个沙箱**：自由运行每次使用一个沙箱；自动评测的每个测试点分别使用全新沙箱，并共享同一评测任务总预算。不同执行不复用可写文件系统、进程或 Python 运行状态。
3. **异步任务模型**：创建任务后返回任务 ID；前端查询任务状态，不用长时间占用 Web worker。
4. **测试数据仅服务端可见**：自动评测的测试输入和期望输出只发送给 Runner，不进入学生浏览器。
5. **默认禁止网络**：学生代码没有公网、VPC、DNS、RDS 或 Web 内网访问能力，不提供按题放开网络的例外。
6. **生产禁用本机回退**：Runner 故障时不得自动退回 Django 本机执行；应明确提示执行服务暂不可用。
7. **队列有界且公平**：优先保证不同学生都有执行机会，单个学生不能占满全部并发和排队容量。
8. **结果兼容现有业务**：最终仍生成现有提交记录、得分和错误摘要；教师统计口径不因拆分 Runner 改变。

## 6. 用户故事与验收

### US-01 运行代码

作为学生，我点击“运行”后可以看到排队和执行状态，并在完成后获得标准输出或错误信息。

验收：

- 空代码、超长代码或超长标准输入在进入队列前被拒绝。
- 创建成功后返回不可猜测的任务 ID 和 `queued` 状态。
- 前端显示“排队中”和“运行中”，完成后显示输出、错误和执行时间。
- 重复点击不会无限创建任务；同一学生达到并发上限时得到明确提示。
- 页面离开或刷新不改变服务端任务所有权，重新进入后可查询本人尚未过期的任务。

### US-02 提交自动评测

作为学生，我提交代码后由隔离环境完成全部测试点，并保存成绩和提交历史。

验收：

- 题目、代码和测试点在任务创建时形成固定快照，后续编辑题目不改变本次评测。
- 所有测试点均在同一个受控任务预算内执行，每个测试点仍相互清理运行状态。
- 评测完成后只由 Web 服务写入生产数据库，Runner 不直接连接数据库。
- 同一提交任务最多生成一条最终提交记录，重复回调或查询不会重复计分。
- 系统错误不伪装成 0 分或答案错误；恢复后允许学生重新提交。

### US-03 资源超限

作为学生，当代码无限循环、占用过多内存、创建过多进程或输出过大时，我能收到可理解的失败原因。

验收：

- 超过墙钟时间后终止整个任务进程组，包括其创建的子进程。
- 内存、进程数、临时空间或输出超过限制时终止任务或截断输出。
- 返回稳定的状态码/业务状态，不向学生展示容器、宿主机路径或内部堆栈。
- 一个资源超限任务不导致其他任务、Web 服务或队列停止工作。

### US-04 课堂集中使用

作为教师，我让整班学生同时运行代码时，系统可以排队而不是直接失去响应。

验收：

- Runner 只按配置的并发数启动沙箱，其余任务进入有上限的队列。
- 调度避免同一学生连续占用全部执行槽位。
- 前端显示排队状态；超过队列容量时返回“系统繁忙，请稍后重试”和建议等待时间。
- 排队超时的任务自动结束，不无限占用队列。
- 登录、课程、小测和教师后台不因 Runner 队列拥堵而明显失去响应。

### US-05 Runner 故障

作为学生或教师，当 Runner 暂时不可用时，我看到明确提示，而平台其他功能仍可使用。

验收：

- Web 能检测 Runner 未就绪、请求超时和异常结果。
- 未开始执行的任务可在恢复后重试或被安全标记为系统失败。
- 已完成结果不会因重复投递而重复写入。
- 不自动在 Web 主机执行学生代码作为降级方案。

## 7. 功能需求

### FR-01 执行任务模型

每个任务至少记录：

- 不可猜测的公开任务 ID。
- 所属用户、任务类型（自由运行/自动评测）和关联题目。
- 代码快照；自动评测还需记录测试点版本或快照摘要。
- `queued`、`running`、`succeeded`、`runtime_error`、`wrong_answer`、`timed_out`、`resource_limited`、`system_error`、`cancelled` 等状态。
- 创建、开始、完成和过期时间。
- 有限的标准输出、标准错误、执行耗时、得分和安全终止原因。
- 幂等键、尝试次数和 Runner 返回的结果版本。

任务状态只能按合法方向迁移；完成状态不可被迟到或重复结果覆盖。

### FR-02 Web 公共接口

- 学生接口继续要求有效登录，且只允许学生访问自己的任务。
- 创建接口验证代码、标准输入、题目、频率、并发数和请求大小后再入队。
- 创建成功使用异步语义返回任务 ID、当前状态和建议轮询间隔。
- 状态接口只返回前端需要的信息，不返回测试点答案、内部容器信息或其他学生数据。
- 原有“运行代码”和“提交”页面操作保持不变；允许调整底层接口契约并同步前端。
- 网络重试和重复点击通过幂等机制避免重复创建同一提交或重复记分。

### FR-03 Web 与 Runner 私有接口

- Runner 接口不得挂在公网 Nginx 路由下。
- Web 与 Runner 使用独立服务身份鉴权，凭据可轮换且不复用用户 Token 或 Django `SECRET_KEY`。
- 请求必须有短有效期并防止重复使用；无效身份、过期请求和重复结果均被拒绝并记录审计。
- Runner 只接收执行所需的代码、标准输入、测试快照和限制参数，不接收数据库凭据或完整用户资料。
- 返回统一、可校验大小的结构化结果；超大或格式异常结果不得写入业务数据库。

### FR-04 沙箱生命周期

每个任务必须：

1. 创建全新的一次性沙箱和临时工作目录。
2. 使用固定版本、最小化的 Python 运行镜像。
3. 以非 root 用户运行，并移除不需要的 Linux capabilities，启用 `no-new-privileges`。
4. 使用只读根文件系统，只允许在受限临时目录写入。
5. 不挂载 Docker socket、宿主机目录、Web 源码、题库目录、用户上传目录或密钥文件。
6. 禁用网络；不能访问公网、DNS、VPC、宿主机、Web 或 RDS。
7. 完成、失败、取消或超时后终止全部进程并删除临时目录。
8. Runner 重启后能够识别并清理遗留沙箱。

### FR-05 默认资源限制

以下是首版安全基线，必须支持通过服务端配置调整，但学生请求不能放宽：

| 限制项 | 自由运行 | 自动评测 |
| --- | ---: | ---: |
| 代码大小 | 64 KiB | 64 KiB |
| 标准输入/单测试点输入 | 64 KiB | 64 KiB |
| 单次执行墙钟时间 | 10 秒 | 每测试点 5 秒 |
| 整个任务总墙钟时间 | 12 秒 | 30 秒 |
| CPU | 最多 1 核 | 最多 1 核 |
| 内存 | 128 MiB | 128 MiB |
| 进程/线程总数 | 16 | 16 |
| 可写临时空间 | 16 MiB | 16 MiB |
| stdout 与 stderr 合计 | 64 KiB | 128 KiB |

- 输出达到上限后立即停止继续收集，并明确标记“输出已截断”；持续疯狂输出的任务可提前终止。
- 时间限制必须终止整个进程组，不能只结束最外层 Python 进程。
- 资源限制结果与学生语法错误、运行错误、答案错误和系统错误分开记录。
- 自动评测总时限到达后停止剩余测试点，并返回超时状态。

### FR-06 队列与限流

- 保留接口级频率限制，并增加基于“排队中 + 运行中”任务数的并发限制。
- 默认每名学生最多 1 个运行中任务、2 个排队任务；具体值可由服务端配置。
- 全局并发数和队列容量由 Runner 宿主机资源决定，不允许无界增长。
- 队列采用兼顾用户公平性的调度方式；同一学生的连续任务不能长期饿死其他学生。
- 任务具有排队有效期；过期、失去所有权或无法执行的任务可安全结束。
- 课堂压测前必须记录吞吐量、平均/95 分位等待时间和拒绝数量。

### FR-07 自动评测一致性

- Web 服务负责读取题目和测试点，形成不可变任务快照；Runner 不读取生产题库文件或数据库。
- 每个测试点使用干净的子执行环境，前一测试点创建的文件和进程不能影响后一测试点。
- 比分计算规则保持现状；测试点未执行完时不得返回伪造的完整得分。
- 评测报告必须限制长度并清理内部路径，不泄露隐藏测试点之外的信息。
- 最终提交记录由 Web 在事务中写入，并与任务 ID 建立唯一关联。

### FR-08 临时文件与数据

- 运行所需代码、输入和测试快照只在任务期间进入临时沙箱。
- 沙箱销毁后不得保留学生可执行文件、子进程或可写层。
- Web 数据库中继续保留业务需要的提交代码和结果；不再把学生代码作为永久 `.py` 文件保存在共享 `submissions/` 目录。
- 任务载荷、队列消息和 Runner 日志不得包含密码、Token、AI 密钥或数据库凭据。
- 普通日志不记录完整学生代码、标准输入、隐藏测试点和完整输出。

### FR-09 健康检查与观察

- Runner 提供不执行学生代码的存活检查和沙箱能力就绪检查。
- Web 的就绪状态不因 Runner 暂时不可用而整体失败，但应提供独立 Runner 状态供运维判断。
- 至少记录任务 ID、状态、耗时、排队时间、资源终止原因和 Runner 实例，不记录敏感载荷。
- 至少可观察队列深度、运行中数量、成功率、超时率、资源超限率、系统错误率和清理失败数。
- 清理失败、异常遗留沙箱和持续队列拥堵必须产生告警信号。

## 8. UI / UX 要求

### 8.1 代码运行区

- 点击“运行”后立即进入“排队中”，随后显示“运行中”。
- 完成后继续在现有输出区域展示 stdout、stderr 和执行时间。
- 超时、内存超限、进程超限、输出过大和系统繁忙使用不同的中文提示。
- 任务处理中禁用重复触发，允许学生编辑代码但明确“本次运行使用的是点击运行时的代码”。
- 前端轮询应有上限并支持页面卸载后停止，不能制造无限请求。

### 8.2 提交评测

- 提交后显示“排队中/评测中”，完成后进入现有成绩与详情流程。
- 系统执行失败时不显示为 0 分，并提供“重新提交”操作。
- 学生运行错误可显示经清理的 Python 错误；不得展示宿主机路径、容器 ID、内部接口或隐藏测试数据。

### 8.3 教师端

- 教师成绩页继续显示现有得分与提交状态。
- 系统失败任务显示“评测服务异常”，与学生答案错误区分。
- 本阶段不新增复杂 Runner 运维后台，运行指标先通过日志和监控提供。

## 9. 安全要求

### 9.1 信任边界

- 学生代码、标准输入、上传文件名和代码输出全部视为不可信数据。
- Web 只信任通过身份和业务校验后的用户请求。
- Runner 只信任通过私有服务鉴权且未过期的任务信封，但仍将其中代码视为恶意内容。
- Web 不直接信任 Runner 返回的大小、状态或文本；写库前再次校验。

### 9.2 密钥与环境

- 沙箱环境变量采用最小白名单，不继承 Runner 控制进程或宿主机环境。
- 沙箱内不得出现数据库连接串、Django 密钥、Runner 服务凭据、云密钥或用户 Token。
- Runner 服务凭据只能存在于控制面，不能挂载进学生沙箱。

### 9.3 网络与主机

- 沙箱没有网络接口或使用等价的强制断网策略。
- Runner 主机安全组不得访问 RDS；生产环境只开放必需的 Web↔Runner 私有通信。
- 沙箱不能访问容器运行时 socket、宿主机设备、特权接口或其他任务命名空间。
- 生产模式检测到特权容器、root 用户、可写根文件系统或网络开启时，Runner 应拒绝进入就绪状态。

## 10. 非功能要求

### 10.1 可用性

- Runner 故障与 Web 故障域分离。
- 任务投递、领取和结果写回具备幂等性，重启不会重复计分。
- 队列与任务状态不能只存在于单个 Web 进程内存中。

### 10.2 性能

- 普通代码在无排队时，点击运行到结果返回的目标中位数不超过 2 秒。
- 本地至少完成 30 个模拟学生的集中运行测试；生产彩排阶段提升到 30–50 个真实并发账号。
- 并发超出容量时以排队或明确拒绝保护系统，不通过取消资源限制追求吞吐量。

### 10.3 可维护性

- Web 与 Runner 契约有明确版本号和自动化契约测试。
- Python 镜像版本固定，不使用浮动 `latest` 标签。
- 所有限制、队列容量和超时通过服务端配置管理，并提供无真实凭据的示例。
- 本地开发、自动化测试和生产模式均不得静默切回 Web 本机执行。

### 10.4 可移植性

- 本地 macOS 通过 Docker Linux 虚拟机验证功能；安全验收以 Linux 容器行为为准。
- Runner 设计可在后续阶段部署到独立阿里云 ECS，不依赖 macOS 专有机制。

## 11. 数据与兼容性

- 需要新增任务记录及其与 `Submission` 的关联，数据库变更前必须备份。
- 既有 `Submission`、成绩、代码和历史查询保持可读。
- 新任务完成后仍更新现有学生最高分和教师统计，不改变历史数据口径。
- 旧 `submissions/*.py` 文件不在本阶段自动删除；先确认数据库中的代码已完整保留，再制定一次性清理清单。
- 前后端接口可以为异步任务调整，但页面入口、题目数据和最终结果体验保持兼容。

## 12. 验收标准与验证方法

### 12.1 静态与配置检查

- Django 业务代码中不存在执行学生代码的 `subprocess`、`exec`、`eval` 或等价调用。
- Web 运行环境不挂载容器运行时 socket，也不具备创建沙箱的宿主机权限。
- Runner 镜像固定版本，并声明非 root、只读根文件系统、能力移除、无网络及资源限制。
- 生产配置不存在“Runner 失败后本机执行”的回退开关。

### 12.2 功能测试

- 自由运行覆盖 stdout、stderr、标准输入、语法错误、运行错误和刷新恢复。
- 自动评测覆盖全对、部分正确、全错、超时、系统失败、重复结果和题目变更后的快照一致性。
- 权限测试证明学生不能查看或操作其他学生任务，教师管理权限不等于 Runner 服务权限。
- 队列测试覆盖单用户并发限制、全局满载、排队过期、公平调度和 Runner 重启恢复。

### 12.3 强制恶意代码测试

以下测试必须在真实隔离沙箱执行，不能只用 mock：

1. `while True: pass`：按时终止且不残留进程。
2. 持续分配内存：触发内存限制，其他任务正常。
3. 循环创建子进程/线程：触发进程数限制。
4. 持续打印：输出截断或终止，Web 内存不随输出无限增长。
5. 创建后台子进程后主程序退出：任务结束时子进程一并消失。
6. 尝试访问公网、DNS、Web 内网和数据库地址：全部失败。
7. 尝试读取宿主机源码、其他学生文件、密钥和环境变量：不能获得目标数据。
8. 尝试写根目录、遍历路径、使用符号链接逃逸：只能写受限临时目录。
9. 任务间写入后读取：后一任务看不到前一任务文件。
10. 构造超大请求或伪造 Runner 结果：在边界处拒绝且不污染数据库。

### 12.4 故障与恢复测试

- Runner 未启动时，代码运行明确失败或等待，其他 Web API 和小测正常。
- Runner 执行中重启后，任务最终进入可解释状态，不永久卡在 `running`。
- 重复投递和重复结果不产生重复提交或重复分数。
- 清理失败能够被检测并告警，恢复流程可清除遗留沙箱。

### 12.5 回归测试

- 后端完整测试通过。
- 前端完整测试通过，生产构建成功，ESLint 无新增错误。
- 学生完成“打开题目→运行→提交→查看得分”的手工验收。
- 教师完成“查看学生提交→查看得分和错误状态”的手工验收。

- Django Web 中直接执行学生代码的路径：2 条降为 0 条。
- Runner 沙箱访问公网、RDS、宿主机源码和其他任务文件的成功次数：0。
- 无限循环、内存耗尽、进程炸弹、后台进程和超大输出测试阻断率：100%。
- 重复结果导致的重复提交或重复记分：0。
- Runner 故障期间，非代码执行核心接口可用率：测试中保持 100%。
- 30 个模拟学生集中运行时，无 Web worker 被学生代码长期占用，无无界队列增长。
- 任务结束后的遗留学生进程和临时目录：0。

## 14. 风险与应对

- **容器不是绝对安全边界**：使用最小镜像、非 root、能力移除、只读文件系统、无网络和独立 Runner 主机形成多层防护。
- **Docker 控制面权限较高**：不把 Docker socket 暴露给 Web 或学生沙箱；Runner 控制接口不开放公网。
- **异步改造影响现有前端**：保留页面操作流程，使用任务状态适配层和契约测试降低回归风险。
- **沙箱启动增加延迟**：先保证安全，通过受控并发、精简镜像和课堂压测优化，不复用学生可写沙箱。
- **队列组件增加复杂度**：优先选择可恢复、有界、可观测的最小方案，在 DEV 文档中确定技术实现。
- **测试点较多导致总时限不足**：保留单测试点与整任务两级配置，由教师题库测试和压测确定合理上限。
- **macOS 验证与 Linux 生产不同**：功能可在本地 Docker 验证，安全门槛必须在 Linux 环境再次执行。

## 15. 回滚原则

- 阶段 5 上线采用显式配置切换到 Runner，但生产环境不得回滚到 Web 本机执行。
- 如 Runner 新链路异常，可暂时关闭“运行”和“提交评测”入口，保留课程浏览、历史成绩、小测和教师管理。
- 数据库迁移必须可回滚；任务表回滚不得删除既有 `Submission` 历史。
- 旧直接执行代码在开发完成后移除；只允许通过版本回退恢复代码，不允许作为生产自动降级路径。
