# 阶段 2：MySQL 接入与数据迁移 PRD

文档状态：已确认（2026-09-01）

## 1. 背景与问题

系统当前仅配置 SQLite。SQLite 适合单机开发，但不适合作为下学期整班教学的正式数据库：并发写入能力有限、备份恢复和运维能力不足，也无法直接使用阿里云 RDS MySQL。

当前数据库基线：

- `backend/db.sqlite3` 约 280KB，SQLite 完整性检查为 `ok`，外键检查异常数为 0。
- 当前共有 20 张非 SQLite 内部表，Django 迁移均已应用。
- 核心数据包括：4 个用户、3 个 Token、9 道 AI 题、9 条编程提交、58 个信息课单元、17 道信息课题、1 场小测、2 条小测提交、1 个对话会话和 2 条对话消息。
- 数据中包含密码哈希、Token、学生代码、AI 对话，以及阶段 3 尚未清理的 `plain_password`，因此备份和导出文件必须按敏感数据处理。

本机当前只有 MySQL 9.4 客户端，没有 MySQL 服务端，也没有 Docker、Podman。Homebrew 可提供 keg-only 的 MySQL 8.0.46；本阶段需要安装并仅用于本地迁移测试，以匹配后续阿里云 RDS MySQL 8.0 目标。

## 2. 目标

1. Django 支持通过环境变量在 SQLite 与 MySQL 8.0 间切换。
2. 生产环境强制使用 MySQL，不允许静默回退到 SQLite。
3. 建立隔离的本地 MySQL 8.0 测试实例、迁移数据库和测试数据库。
4. 验证仓库全部 Django migration 可在空 MySQL 8.0 数据库执行。
5. 提供可重复的 SQLite 在线备份、业务数据导出、MySQL 导入和迁移校验工具。
6. 明确处理用户、权限组、Token、题库、提交、小测、多对多关系和对话的依赖顺序。
7. 通过行数、主键集合、外键、确定性摘要和业务抽查证明迁移前后数据一致。
8. 至少完成两轮“清空目标库 → migrate → import → verify”，证明流程可重复。

## 3. 非目标

- 不在本阶段创建或购买阿里云 RDS。
- 不把 MySQL 服务暴露到局域网或公网，只监听本机。
- 不在本阶段删除 `plain_password`；阶段 2 原样、安全迁移，阶段 3 再完成业务改造和历史清理。
- 不修改 Token 生命周期或重新签发 Token。
- 不修改现有表的业务结构、年级枚举、小测逻辑或 Runner。
- 不迁移 `problems/`、`media/`、`submissions/` 等文件系统内容；本阶段只迁移数据库，文件将在后续部署阶段单独处理。
- 不把本地 MySQL 服务配置当作未来阿里云 RDS 的最终参数；本阶段只验证数据库兼容性和迁移流程。
- 不修复阶段 1 已记录的 2 项 Django 基线失败及前端工具链停滞。

## 5. 功能需求

### 5.1 数据库环境配置

新增以下后端环境变量：

- `DJANGO_DB_ENGINE`：`sqlite` 或 `mysql`。
- `DJANGO_DB_NAME`
- `DJANGO_DB_USER`
- `DJANGO_DB_PASSWORD`
- `DJANGO_DB_HOST`
- `DJANGO_DB_PORT`
- `DJANGO_DB_CONN_MAX_AGE`
- `DJANGO_DB_CONNECT_TIMEOUT`
- `DJANGO_DB_TEST_NAME`

规则：

1. development 和 test 默认仍使用 SQLite，避免强制依赖本地服务。
2. 显式选择 `mysql` 时，上述 MySQL 连接参数必须经过格式校验。
3. production 必须设置 `DJANGO_DB_ENGINE=mysql`；使用或回退 SQLite 时拒绝启动。
4. MySQL 连接使用 `utf8mb4`、严格 SQL 模式和 Django 推荐的 `read committed` 隔离级别。
5. 数据库密码只来自环境变量或被忽略的本地环境文件，不写入代码、日志、报告或命令历史示例中的真实值。
6. 增加受支持的 MySQL Python 驱动，并保留 SQLite 作为开发和快速单元测试后端。

### 5.2 本地 MySQL 8.0 测试环境

1. 使用 Homebrew 安装 keg-only `mysql@8.0`；不替换系统当前 MySQL 9.4 客户端链接。
2. 测试服务仅监听 `127.0.0.1`，不配置开机常驻，不开放网络端口。
3. 建立独立的迁移目标库和 Django 测试库，均使用 `utf8mb4`。
4. 建立最小范围的本地测试账号，仅拥有两个测试库所需权限，不使用 root 运行 Django。
5. 凭据保存到被 Git 忽略的本地文件，示例文件只使用占位值。
6. 文档必须包含启动、停止、状态检查和完全移除本地测试实例的步骤。

资源变更说明：实施本阶段需要执行 Homebrew 安装 MySQL 8.0，会占用本机磁盘并增加一个可手工启动/停止的本地服务；确认本 PRD 即表示同意在 DEV 再次确认后执行该安装。

### 5.3 SQLite 一致性备份

1. 备份前执行 SQLite `integrity_check` 和 `foreign_key_check`，失败时禁止继续。
2. 使用 SQLite 在线备份 API 生成一致性副本，不直接在应用可能写入时复制数据库文件。
3. 备份文件名包含 UTC 时间，文件权限限制为当前用户可读写。
4. 同时生成 manifest，记录源文件路径、大小、SHA-256、备份 SHA-256、创建时间、SQLite 版本和数据模型行数。
5. 备份、导出和 manifest 默认写入 Git 忽略目录，避免敏感数据进入仓库。
6. 任何迁移演练都只读取备份副本，不直接从正在使用的 `db.sqlite3` 导出。

### 5.4 业务数据导出

导出范围：

1. 用户和用户的组/权限关系。
2. DRF Token。
3. AI 课程题目与提交。
4. 信息课单元、题目、小测、小测与单元多对多关系、小测提交。
5. AI 对话会话与消息。

默认不导出可重新生成或无业务价值的数据：`contenttypes`、系统权限定义、admin 日志、Django session。迁移目标执行 migration 时会重新生成 ContentType 和 Permission。

导出要求：

- 保留业务主键、外键、多对多关系、时间戳、JSON、中文、代码和长文本。
- 按依赖顺序生成版本化 fixture 或等价中间文件。
- 每个导出文件记录 SHA-256 和行数。
- 不在终端或报告中打印密码、Token、学生代码或完整对话内容。
- 导出工具可重复运行，并且同一备份产生确定性一致的业务摘要。

### 5.5 MySQL 导入

1. 导入前确认目标数据库引擎确为 MySQL，且业务表为空；不满足条件时拒绝执行。
2. 先执行全部 Django migration，再导入业务数据。
3. 按“用户/组 → Token → 题目/单元 → 提交/题库 → 小测及多对多 → 小测提交 → 对话会话 → 对话消息”顺序导入。
4. 在事务和约束检查保护下执行；任何一步失败则整轮业务导入失败，不留下被误判为成功的部分数据。
5. 导入后重置 MySQL 自增序列，确保新建记录不会与迁移主键冲突。
6. 导入工具不得自动删除或覆盖非空目标库；重建测试库必须由单独、明确的本地测试命令完成。

### 5.6 迁移校验

校验工具至少检查：

1. 所有导出业务模型的行数一致。
2. 各模型主键集合一致。
3. 外键和多对多关系无缺失。
4. 对每个模型的规范化序列化内容生成 SHA-256，源 manifest 与目标结果一致。
5. MySQL `check --database`、migration 状态和数据库连接健康检查通过。
6. 内部抽查密码哈希和 Token 值保持一致，但输出只显示通过数量，不显示值。
7. 使用现有 `plain_password` 只在进程内抽查 Django `check_password`，报告不输出用户名或密码；阶段 3 将删除该字段和做法。
8. 抽查题目中文/代码、提交分数、小测 JSON、多对多单元关系、对话消息长文本；报告只输出模型、主键和通过/失败，不输出敏感正文。

### 5.7 可重复演练

至少完成两轮独立演练：

1. 从同一 SQLite 备份生成导出。
2. 重建空 MySQL 测试目标库。
3. 执行 migration。
4. 执行导入。
5. 执行完整校验。
6. 两轮均生成成功报告，目标业务摘要必须一致。

## 8. 非功能需求

### 8.1 安全

- MySQL 只监听本机，测试用户使用最小权限。
- 敏感备份目录被 Git 忽略，文件权限为 `0600`，目录权限为 `0700`。
- 日志、manifest 和报告不包含数据库密码、Token 值或明文密码。
- 所有删除/重建操作先验证目标数据库名和主机，不允许作用于未知或生产目标。

### 8.2 完整性

- 源 SQLite 必须通过完整性和外键检查。
- 迁移必须保留主键、时间戳、外键、多对多和 JSON 内容。
- 行数相同但内容摘要不同仍判定失败。
- 导入失败不得生成成功报告。

### 8.3 可重复性

- 全流程使用仓库内命令和文档，不依赖手工逐表复制。
- 相同备份重复导入空库应得到相同摘要。
- 未来更换为 RDS 连接变量后，可复用相同的导出、导入和校验工具。

### 8.4 可恢复性

- 源 SQLite 始终只读参与演练。
- 每轮操作前有带 SHA-256 的一致性备份。
- MySQL 导入失败时可丢弃本地测试库并从备份重新开始。

## 11. 风险与回滚

- 风险：Homebrew MySQL 8.0 与现有 9.4 客户端路径冲突。对策：使用 keg-only 绝对路径，不执行 `brew link --force`。
- 风险：MySQL 严格模式暴露 SQLite 未发现的数据问题。对策：先在空库执行 migration，再逐模型导入并在失败时输出模型和主键，不输出敏感正文。
- 风险：ContentType/Permission 主键在不同数据库不一致。对策：由 migration 重建系统权限，业务组/权限关系使用自然键或确定性映射。
- 风险：自关联 Unit、多对多 QuizSession.units 导入顺序错误。对策：显式排序并在约束保护下导入，完成关系摘要校验。
- 风险：备份含明文密码和 Token。对策：权限收紧、Git 忽略、报告脱敏；阶段 3 尽快清理明文密码。
- 风险：误清空错误数据库。对策：重建命令只接受 `127.0.0.1` 且数据库名必须包含固定 `stage2` 标识，否则拒绝。
- 回滚：停止 Django MySQL 配置并改回 `DJANGO_DB_ENGINE=sqlite` 即可使用原数据库；迁移工具不修改源库。失败的本地目标库可安全重建，备份保留供重新演练。
